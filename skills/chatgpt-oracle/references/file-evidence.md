# 文件传输与内容识别的证据

在判断上传、导出、图片或文件是否“已读到”，或交付相关结论时读取。按任务目的选择所需证据，不把不同阶段互相替代。

本页的 Library、pointer、ZIP 与源附件下载针对 ChatGPT；字节传输、页面挂载和内容识别的区别也适用于 Gemini，其实际能力边界见 [gemini.md](gemini.md)。

## 四种结果

| 已验证结果 | 可以支持 | 仍不能支持 |
| --- | --- | --- |
| messages / markdown 分页到 EOF，长度与哈希匹配 | 对应正文视图完整取回 | 所有附件字节下载完成或接收模型看过图片 |
| attachments 清单与消息关联 | 文件名、大小、类型、可用状态已列出 | ZIP 内文件、图片画面或文件正文已读取 |
| 附件 GET / file_ref 内容取回，字节证据匹配 | 指定文件表示已传输 | 模型理解了内容，或表示与原始上传字节完全一致 |
| 接收端实际打开图片、读取文件或解压检查所需内容 | 指定画面、文字或文件内容已被查看 | 未检查的附件全量、精确 OCR 或未知原件一致性 |

给 Web 上传时另区分：服务收到字节 → 页面附件验证 → 回答引用附件内部具体内容。上传回执与页面 verified 不单独证明 Web 模型读取成功；具体 ZIP 核对见 [uploads.md](uploads.md)。

模型声称“已读取”或给出引文仍须核验。需要确认 Web 实际使用附件时，将它引用的标识、数值或原句与本地原件比较；文件名准确、引用格式逼真均不能替代比较。若内容不符，记录“附件读取未通过”，不能把模型自述升级为证据。`COMPLETE`、`research.report_complete` 表示生成和结果回收的技术状态，不保证回答正确或附件已读。

若 Main 解压 ZIP 后另传 TXT，记录原 ZIP、条目与派生材料的关联；模型准确引用派生 TXT 只证明它使用了该材料，不证明自行解包或直接读取了 ZIP。没有可用读取能力时，可按讨论目的由 Main 提供已核验的语义快照，并明确这是 Main 提取的事实；不能据此宣布原始附件读取验收通过。

用户要求判断图片或附件内容时，取得所需文件表示，并交给接收客户端实际支持的图片/文件读取工具。ZIP 要解压检查相关文件。正文引用附件、文件名、pointer、base64 文本、哈希和下载成功本身均不替代实际查看。

交付时点明查看了哪个附件、哪个区域或具体内容；未取回或未查看的项保留缺口。只需正文的任务可以只读正文，但不能外推为附件已读。

## 输入附件与生成附件

两类附件都在核对范围内。按对应消息与文件身份关联，避免只检查生成文件而遗漏用户输入图片、ZIP 或文本。

一个用户文件可能同时有 `libfile_…` Library 引用和 `file_…` 图片 pointer。Library 原件不可下载不单独证明图片丢失；pointer 下载成功也不证明原件恢复。不要将两种表示重复算成两个文件。

当前导出适配器的 Library 原件下载存在缺口，ZIP/Markdown 元数据不等于原始文件内容。不能将缺少可验证下载源写成“原件已失效”或“ChatGPT 没有原件”。当前实例的差异见 [compatibility.md](compatibility.md)。

## 图片可用性与原件

派生图可能足以识别界面、控件和主要文字；归档 partial 或原件不可用，不单独决定图片对当前任务是否可用。不能据此保证小字的精确 OCR。

客户端保存的原始上传文件，或有原件依据的下载来源，可以作为补充。ChatGPT 下载所得仍可能是 pointer 派生图；客户端补充原文件也不证明服务恢复了 OpenAI 原件。

细节不足时指定文件、消息、区域和待识别内容，再按 [uploads.md](uploads.md) 选择补充或回传。接收客户端是否支持某种图片/文件输入决定能否实际读取；MCP 传输成功不赋予模型该能力。不把猜测写成识别结果。
